# Profile-aware Turn-taking：当前判断、问题与下一步计划

日期：2026-07-31

## 一、先说结论

1. **研究方向仍然可以做，但真正的方法卖点不能只是“加入 profile”或“做 hidden/given/shuffled 对照”。** 更像方法贡献的方案是：设计一个**双时间尺度的 Profile State Adapter**——快速分支持续编码当前音频和部分转写，慢速分支维护稳定人物信息并因果更新 relationship/situation，再用门控融合决定当前事件应依赖哪些 profile 字段。hidden/given/shuffled 只是证明该方法是否有效的验证手段。
2. **Qwen2.5-Omni-3B 的 profile pilot 已经跑通。** 输入同时包含音频、部分转写和 profile；两批几乎独立的50条中，真实 profile 都比隐藏 profile 准确，第二批也优于错误 profile。当前输出仍集中在 C/I，所以这是正向初步结果，还不是最终五分类结果。
3. **“实时语音模型能聊天”不等于“它能用提示词预测下一话轮标签”。** 实际语音系统常把 VAD、停顿阈值、打断检测和模型回复组合起来。模型能实时生成回复，并不能证明它内部会稳定输出 BC、T、I 等未来事件标签。
4. **SBCSAE 的 profile 并非完全雷同。** 当前核心数据有 16 段双人会话、32 位说话人、32 份不同的完整 profile。但 16 段会话意味着只有 16 个相对独立的关系和场景，这是比“事件条数少”更重要的限制。
5. **现在不为 Omni 单独训练 adapter。** Omni 继续承担低成本的输入排错、零样本基线和提示词实验；正式方法使用独立、可迁移的 profile 融合模块。

## 二、对目前三个判断的修正

### 1. 之前的通用大模型是不是都只有约 50%

这个说法只对了一部分。

[Talking Turns（ICLR 2025）](https://openreview.net/pdf?id=2e4ECh0ikn)把实验分成两种：

- **理解已经发生的事件**：音频中已经出现换人、回应或打断，让模型判断有没有发生。
- **预测未来事件**：音频在预测点停止，让模型猜接下来是否换人、回应或打断。

在“预测未来”任务中，论文使用四个平衡的二分类任务。开源音频大模型大多接近 50%：

| 模型 | 换人 | Backchannel | 打断 | 打断后取得话轮 |
|---|---:|---:|---:|---:|
| 随机猜测 | 50.0 | 50.0 | 50.0 | 50.0 |
| Qwen2-Audio-Instruct | 46.5 | 49.3 | 51.5 | 54.4 |
| Qwen-AudioChat | 49.9 | 52.1 | 52.3 | 50.8 |
| Whisper + GPT-4o | 62.2 | 48.6 | 49.3 | 50.0 |
| 监督训练的专用模型 | 78.6 | 75.1 | 74.9 | 65.6 |

因此，论文支持的准确表述是：

> 通用音频大模型用零样本提示词做“未来话轮预测”时接近随机；但经过监督训练的专用话轮模型明显高于随机，说明任务本身可以学习。

还需要注意两点：

- 论文测试的是 Qwen2-Audio，不是我们现在的 Qwen2.5-Omni-3B。
- 论文的 50% 是平衡二分类准确率；我们旧实验是五分类，数字不能直接等同。

### 2. 实时语音 AI 为什么能聊天，却不能稳定完成这项测试

这并不矛盾。一个实时语音系统可以通过下面的组合正常工作：

1. VAD 检测用户是否开始或停止说话；
2. 静音计时器决定等待多久；
3. 用户再次开口时立即停止系统语音；
4. 大模型负责理解内容和生成回复。

例如，[OpenAI Realtime API](https://platform.openai.com/docs/api-reference/realtime)会把简单 VAD 和语义 VAD 作为独立的 turn detection 配置，而不是要求对话模型每 40 ms 输出一个话轮类别。[Qwen2.5-Omni 官方说明](https://github.com/QwenLM/Qwen2.5-Omni)的“实时交互”主要表示可以流式接收多模态输入并流式生成，不等于它在 Talking Turns 的未来事件标签上经过专门训练。

所以我们需要把两个问题分开：

- **模型是否听懂了已经发生的声音和话轮事件？**
- **模型是否能预测尚未发生的下一事件？**

如果模型能完成第一项，却不能完成第二项，说明问题主要在未来预测能力，而不是音频没有输入。

### 3. 统一输出是不是输入方法有问题

专项排查已经把几个可能原因分开：

1. ASR 对 8 条音频全部有输出，平均词重合 F1 为 0.64，说明音频输入链路是通的；
2. 把文字和音频顺序调换，塌缩没有消失；
3. 改成 Talking Turns 风格提示，结果仍为 4/8；
4. 把真实音频换成静音或同任务的相反音频，8 条答案全部不变，但这两组仍保留了正确的部分转写；
5. 把两个答案的书写顺序交换后，6/8 条跟着位置改变。

因此现在可以更准确地说：**问题不是音频没有传入，也不能由这8条推出模型无法判断；原来的生成式二选一受到答案位置偏置。换成决策式五分类后，50条静音对照中17条改变答案，并且 profile 能改变部分预测。**

## 三、我们的数据现在是什么样

### 1. 音频和事件

当前使用 SBCSAE 中的 16 段核心双人自然对话：

| 内容 | 当前数量 |
|---|---:|
| 双人会话 | 16 |
| 总时长 | 6.43 小时 |
| 连续说话片段（IPU） | 9,218 |
| 五类参考事件 | 16,144 |

五类事件分布：

| 标签 | 数量 |
|---|---:|
| C：当前说话人继续 | 4,931 |
| BC：简短回应 | 1,302 |
| T：自然换人 | 2,525 |
| I：重叠或打断 | 1,301 |
| NA：无人说话 | 6,085 |

### 2. Profile 的组成

当前核心数据有 32 位说话人，对应 32 份不同的完整结构化 profile：

| 字段 | 当前种类 |
|---|---:|
| 年龄段 | 8（含 unknown） |
| 性别记录 | 2 |
| 社会角色/职业 | 25 |
| 组合背景描述 | 30 |
| 双方关系 | 5 |
| 交谈场景 | 5 |

关系分布：

| 关系 | 会话数 |
|---|---:|
| 家庭 | 5 |
| 伴侣 | 4 |
| 朋友或同辈 | 3 |
| 同事 | 2 |
| 专业人员与客户 | 2 |

场景分布：

| 场景 | 会话数 |
|---|---:|
| 日常社交 | 7 |
| 家庭或居家对话 | 4 |
| 协作任务 | 2 |
| 工作或商务 | 2 |
| 医疗咨询 | 1 |

因此，问题不是 profile 内容完全相同，而是：

- 16,144 个事件反复来自 16 段会话；
- 同一会话中的许多事件共享同一份关系和场景；
- 不能把 16,144 条当成 16,144 个独立 profile 样本；
- `relationship` 和 `situation` 目前来自整段会话说明并经过人工整理，不是模型根据预测点之前的历史动态得到的。

### 3. Profile 字段怎样分层

第一阶段建议固定成三组，方便后续消融：

| 组别 | 字段 | 第一阶段 | 第二阶段 |
|---|---|---|---|
| 稳定个人信息 | 年龄段、性别记录 | 会话开始时给定 | 不更新 |
| 稳定社会背景 | 社会角色、教育/地区等背景 | 会话开始时给定 | 不更新 |
| 关系与场景 | relationship、situation | 先使用整理后的值作为上限 | 根据截止当前的历史动态更新 |

性别、地区和族裔等字段可能带来敏感属性与说话人身份泄漏。正式论文应把它们单独做消融，主结果优先报告社会角色、关系和场景。

### 4. 数据是否符合需要

我的判断是：

- **适合做方法原型和第一轮 profile 有效性验证；**
- **不适合单独支撑“普遍适用于所有关系和场景”的强结论。**

现在不建议立刻放弃 SBCSAE，因为音频、时间转写和人物资料已经整理完成。更稳妥的做法是：

1. SBCSAE 继续作为主原型数据；
2. 从五类参考事件中冻结一小批技术测试样本；
3. 方法跑通后，再加入第二个数据集做外部验证。

候选第二数据集可优先调查 [NoXi](https://multimediate-challenge.org/publications/cafaro17_icmi/)。它是自然的双人 novice–expert 对话，包含多模态数据及话轮相关标注，适合验证“社会角色影响话轮”；缺点是关系类型较固定，不能完全替代 SBCSAE。

## 四、我们现在给 Omni 的真实输入和输出

模型：Qwen2.5-Omni-3B，Q8_0 量化，`llama.cpp` 本地推理。

这是一项零样本提示实验，没有训练模型。

每条请求包含：

1. 截止预测时刻 `t` 的单声道音频，音频结束位置就是 `t`；
2. 与音频匹配、且结束时间不超过 `t` 的带说话人部分转写；
3. hidden 条件下的 profile 占位文字，或后续 given 条件下的真实 profile；
4. 一个具体的二分类预测问题。

当前提示词的核心形式是：

```text
请听一段双人对话。
音频只包含过去，并且恰好在预测时刻 t 结束。
只预测 t 之后发生什么，不要声称听到了未来音频。

[换人 / backchannel / 打断 / 打断后取得话轮中的一个二分类问题]

截止 t 的带说话人转写：
[speaker_00 ...]
[speaker_01 ...]

Profile：
[hidden / given / shuffled]

只能返回两个指定答案中的一个。
```

请求中没有未来音频、未来转写、目标答案或自动标注依据。hidden、given、shuffled 三组只允许修改 profile。

## 五、现在已经得到什么结果

### 1. 旧的 500 条五分类

旧实验每类抽取 100 条，共 500 条。模型严重偏向 `I`：

- hidden：445/500 预测为 I；
- given：477/500 预测为 I；
- shuffled：475/500 预测为 I；
- given 没有稳定优于 hidden。

这批结果说明当时的生成式五分类发生了输出塌缩，不能作为 profile 有效性的证据。

### 2. 修正规则后的 50 条二分类

新实验按 Talking Turns 的四个任务分别做平衡二分类：

| 任务 | 正确数 | 输出情况 |
|---|---:|---|
| Backchannel | 6/12 | 12 条全部预测“不会发生” |
| 换人 | 6/12 | 12 条全部预测“当前说话人继续” |
| 打断 | 7/12 | 两种答案都出现 |
| 打断后取得话轮 | 7/14 | 14 条全部预测“第二人取得话轮” |
| 总体 | 26/50（52%） | 总体看似多样，三个子任务内部塌缩 |

这 52% 与 Talking Turns 中开源模型接近随机的现象一致，但仍不能写成复现结论，因为：

- 只有 50 条；
- 本地推理后端与论文不同；
- 三个任务内部固定输出一个答案。

### 3. 8 条专项技术排查

本轮从四个二分类任务中各取一条正例和一条反例，共 8 条，运行 10 种条件、80 次请求：

| 检查 | 结果 |
|---|---:|
| 当前未来预测 | 4/8 |
| 已发生事件识别 | 4/8 |
| Talking Turns 风格提示 | 4/8 |
| 音频放在文字前面 | 3/8 |
| 静音替换后答案改变 | 0/8 |
| 错配音频后答案改变 | 0/8 |
| 交换答案顺序后保持原语义 | 2/8 |

这轮排查确认模型能够接收并转写音频，也发现原来的二选一提示存在答案位置偏置。由于静音和错配组仍保留正确转写，0/8不能解释成模型无法判断。后续已经改用决策式五分类并完成 profile 对照。

### 4. 两批50条 Profile 对照

主输入同时包含音频、部分转写和 profile。两批各50条，只重合1条：

| 样本组 | hidden 准确率 | given 准确率 | shuffled 准确率 |
|---|---:|---:|---:|
| 第1批 | 26% | **28%** | 26% |
| 第2批 | 18% | **26%** | 20% |

两批真实 profile 都优于隐藏 profile；第二批也优于错误 profile。当前预测仍集中在 C/I，下一步继续用当前3B改进层次化五分类。

## 六、论文贡献应该怎样重新表述

建议把论文主线收束成一个核心方法和两个扩展贡献。对照实验本身不算贡献，只负责证明方法。

### 核心方法：双时间尺度 Profile State Adapter

模型包含两个不同更新速度的状态：

- **快速对话状态**：随当前音频和因果部分转写持续更新，负责韵律、停顿、重叠与当前语义；
- **慢速 profile 状态**：稳定保存年龄段和社会角色，并只根据过去对话低频更新 relationship/situation；
- **字段门控融合**：针对每个预测事件，自动决定当前更应依赖声学线索、文本线索还是某个 profile 字段。

输出为 C / BC / T / I / NA。这个方法可以接在不同音频编码器或 VAP 类模型上，不为 Omni 单独设计。

### 扩展贡献 1：带不确定性的因果动态 Profile

relationship/situation 不直接作为永远正确的静态文本，而是由截止当前的对话历史产生一个带置信度的状态；低置信度时门控层应减少对它的依赖。这样可以处理关系和场景逐步明确或发生变化的真实情况。

### 扩展贡献 2：Profile 一致性训练

训练时加入正确 profile、隐藏 profile 和错误 profile：

- 正确 profile 帮助分类；
- 缺少 profile 时仍能依靠音频和转写完成基础预测；
- 错误 profile 不应让模型无条件改变答案。

这里的方法贡献是**训练目标和门控机制**，而不是三组测试本身。hidden/given/shuffled 仍作为最后的验证协议，检查模型是否真正使用正确 profile。

这一方案比“静态人物卡 + 一个分类头”更像可以单独发表的方法。

相关工作的边界需要说清楚：

- [Prompt-Guided Turn-Taking Prediction（SIGDIAL 2025）](https://aclanthology.org/2025.sigdial-1.9/)把 “faster / calmer” 等文本提示 embedding 注入训练过的 VAP；它证明提示可以控制话轮，但不是使用真实说话人 profile。
- [Modeling Turn-Taking Speed and Speaker Characteristics（SIGDIAL 2025）](https://aclanthology.org/2025.sigdial-1.2/)发现角色、朋友/陌生人和人格与话轮速度有关；它支持我们的动机，但主要预测间隔分布，不是五类事件模型。
- [ACL 2025 多模态话轮与 backchannel 预测](https://aclanthology.org/2025.acl-long.743/)说明音频、文本和视觉的训练式融合有效，也说明正式方法不能只依赖零样本提示词。

## 七、下一步的具体实施方案

### 第 1 步：一天内完成 Omni 技术排错

目的：不是追求 profile 提升，而是确认模型、输入和提示词没有明显操作错误。

固定一组开发样本，不用于最后报分，依次做：

1. **听音检查**：让模型转写或回答音频中已经说出的内容，确认真正收到音频。
2. **已发生事件识别**：把事件完整放进音频，让模型判断是否已经出现换人、BC 或打断。
3. **未来事件预测**：音频在事件之前结束，再预测下一事件。
4. **音频敏感性检查**：同一问题替换成静音或错误音频，观察输出是否合理改变。
5. **输入顺序检查**：在开发样本上比较“音频→文字”和“文字→音频”，同时核对 ASR；选定后冻结。
6. **提示词检查**：先复现 Talking Turns 的原始二分类提示，再增加我们的因果转写和 profile。提示词只能在开发样本修改。

这一阶段输出一张表：

| 检查 | 通过标准 | 说明 |
|---|---|---|
| 能听音 | 大部分音频内容能被正确复述 | 音频通路正常 |
| 能识别已发生事件 | 每个任务两种答案都能出现 | 任务说明可理解 |
| 能预测未来 | 输出不固定为一个答案 | 才能继续 profile 比较 |
| 对音频敏感 | 静音/错配音频会产生合理变化 | 没有只看文字 |

如果本地 `llama.cpp` 失败但官方 Transformers 运行成功，说明主要是本地推理实现问题；如果两者都能识别事件但都不能预测未来，说明主要是零样本预测能力问题。

### 第 2 步：用当前参考数据跑一次小型 Omni 报告

只保留五类，不做七类。

从当前 C、BC、T、I、NA 参考事件中按任务平衡抽取一组测试样本，冻结后不再根据模型结果修改。

在这组数据上运行：

- hidden；
- given；
- shuffled。

只汇报：

- 每个任务正确率；
- 每种答案输出多少次；
- given 相比 hidden 改对了多少条、改错了多少条；
- shuffled 是否与 given 明显不同。

即使结果没有提升，只要输入和标签可靠，也是一项可以向老师汇报的零样本结论。

### 第 3 步：决定数据是否需要扩展

完成小型 Omni 测试后再决定，不提前换掉 SBCSAE。

| 观察 | 决策 |
|---|---|
| profile 分组有差异且基线可运行 | 继续 SBCSAE 主实验 |
| Omni 仍塌缩但输入审计全部通过 | 保留为零样本负结果，开始训练正式方法 |
| profile 与事件高度绑定于少数会话 | 增加更多双人窗口或第二数据集 |
| 静态 profile 有趋势但会话数太少 | 用 NoXi 等数据做外部验证 |

### 第 4 步：训练正式的通用方法，而不是 Omni 专用 adapter

正式模型建议由四部分组成：

1. 音频编码器：学习韵律、停顿、重叠和说话活动；
2. 因果文本编码器：读取截止当前的部分转写；
3. 结构化 profile 编码器：每个字段单独 embedding，并允许字段为 unknown；
4. 融合层与五分类头：输出 C / BC / T / I / NA。

自然语言 profile 继续作为 Omni 的 prompt baseline；主方法优先使用结构化 field embedding，因为：

- 数据量小，固定字段更容易学习；
- 可以明确删除或打乱某一个字段；
- 第二阶段动态更新时，只需替换 relationship/situation 的状态；
- 不会把 prompt 写法本身混入 profile 效果。

正式实验至少包含：

| 实验 | 要回答的问题 |
|---|---|
| 音频 + 转写 | 没有 profile 的基线有多强 |
| + 正确 profile | profile 是否提高预测 |
| + shuffled profile | 模型是否真的利用正确内容 |
| 只加 relationship/situation | 关系和场景是否是主要来源 |
| 删除敏感字段 | 提升是否依赖性别、地区或族裔泄漏 |
| 动态推断 relationship/situation | 第二阶段在真实未知条件下是否仍有效 |

### 第 5 步：形成论文证据链

最终论文不依赖某一次 Omni 的好结果，而由下面的证据链组成：

1. 通用 MLLM 零样本基线：说明现成模型能否直接利用 profile；
2. 固定的五类事件参考与严格输入审计；
3. 训练式 profile-aware 方法：证明方法本身是否有效；
4. hidden/given/shuffled 与字段消融：证明提升来自正确 profile；
5. 动态更新实验：证明关系和场景不必永远由人工提前给出；
6. 第二数据集：证明效果不只来自 SBCSAE 的 16 段会话。
